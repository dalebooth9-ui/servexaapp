
- Live (non-scanned) report PDFs load signatures via authenticated storage download, wait for in-flight signature saves, and refuse to render (logging `signature_missing_on_pdf`) if a saved signature can't load — why: silent unsigned PDFs reached customers.
- The service-worker storage cache never stores opaque responses — why: opaque copies broke later CORS image loads in PDF generators.
- Before/after slots store durable storage references and link existing job photos without copying or deleting the source — why: slot changes must update reports immediately while preserving the job photo library.
- Report site photos: selection is stored per report as `_site_photo_excluded` (normalised storage-path keys) and photos render on separate pages after the sign-off — why: keeps single-sheet reports on one page and matches every photo source.
- Wet/visual report switching keeps one response row, changes only template_id and stores `_mode_switch` in the answers; pairs live in `src/lib/reportModeSwitch.ts` — why: no data loss on switch/back and new pairs need only a config entry.
- Customer PDFs for active wet/visual switches use the visual report identity and never print switch reasons or notes — why: switch context is office-only.

- Site Visit Reports live in `site_visit_reports` (not job sheet templates); photos link existing job photos via `site_visit_report_photos` (durable storage_ref + stable finding_id) — why: written reports differ from checklists and photos must not shift between findings.
- Site Visit Reports are created immediately on open (prefilled by `src/lib/siteVisitReportPrefill.ts`) and autosave to the row plus an `autosave_svr_<id>` local copy — why: drafts survive signal loss and closed tabs.
- Site Visit Reports start from one shared Extra section; optional selected job-sheet comments are combined under one source heading — why: a full written report is an occasional job-level extra, not an action belonging to every completed report.
- Site Visit Report approval/unlock go through security-definer RPCs (approve_site_visit_report / unlock_site_visit_report) guarded by a trigger; approval raises defects for 'us' recommendations and stores defect_id on the recommendation — why: only office approves, locks are server-enforced, and defects are never duplicated.
- Site Visit Report PDFs are built client-side in src/lib/siteVisitReportPdf.ts (shared renderPdfHeader, org logo/brand colour, red brand colours fall back to blue); approved PDFs are filed as job_documents (storage:// ref, shareable) and portal users open them via the portal-document-url function — why: no existing template changes and portal users have no direct storage access.
- The 'new version' banner's Update now drops the app service worker before reloading (reloadToLatest in src/pwa/registerSW.ts) — why: a plain reload is answered by a stale worker's cached page, leaving devices stuck on old builds.

- Weekly planner renders one fixed droppable cell per engineer/date and uses pointer-position collisions for visit moves; cards remain per-day even for multi-day jobs — why: spanning zones and centre-based collisions displaced drop targets.
- The app service worker uses prompt mode and the page never reloads itself; the update notice shows once per deployed version, only on dashboard/job list — why: auto-reloads wiped engineers' in-progress reports.
- Open job-sheet forms persist per job (`open_form_<jobId>`) and flush drafts on pagehide/hidden — why: a reload must return to the same report with answers.
- Job completion classifies job sheets by actual template answers: untouched drafts become `not_used`, started drafts remain editable, and only `submitted` sheets enter office/customer PDFs — why: unused or unfinished forms must not block field completion or leak blank reports to customers.
- Dry and wet risers are rows in `assets` (asset_type/category "Dry Riser" / "Wet Riser", helpers in src/lib/dryRisers.ts); sheets link via `riser_asset_id` in answers, sync matches the chosen asset of the same type then site+type+lower(riser_location), and failures/unknowns go to `asset_review_flags`; wet sheets pick the riser above the form (no template field) — why: no duplicates, no cross-type links, no silent sync failures.
- Riser sticker status (assets.label_status) and wrong-riser flags change only through security-definer RPCs (mark_assets_label_printed, mark_asset_label_placed, report_wrong_riser, add_site_risers, lookup_asset_by_tag); stickers/PDF QRs encode https://servexaapp.com/r/<asset_tag> via src/lib/riserStickers.ts — why: engineers can't update assets directly and every sticker must resolve on the primary domain.
- QR Start service uses start_riser_scan_service with an org/site/London-day transaction lock, assignment checks and per-riser response reuse; scan URLs use the existing engineer view/event listener and return to its progress list after persisted submission — why: double taps cannot create jobs or reports twice, and engineers never pass through office template selection.
- Sticker logo geometry is defined once in STICKER_CONTENT and measured after cropping image whitespace; startPosition offsets the unchanged L4778 grid — why: source-logo padding cannot shrink the printed brand or disturb sheet alignment.
- Duplicate sites are merged only via `merge_sites`/`undo_last_site_merge` RPCs (admin, one transaction, per-merge row in `site_merge_log` recording moved ids); merged sites are soft-deleted (`deleted_at`, `merged_into_site_id`) and hidden by a restrictive RLS policy — why: nothing is lost and every merge can be undone. Importers resolve an exact name matching several sites to the one with the most data (`pickSiteWithMostData`).
- Dry-riser visits are created transactionally via `create_riser_visit`, with existing per-riser response links, `_riser_visit` context and `_visit_prefill` baseline excluded from started-report detection; blank paperwork opts into existing PDF/Word builders, while due reminders derive from inspection history and persist cycle-scoped state on assets — why: one job cannot be partially created, results stay blank, and reminders never book jobs or reset from remedials.
- Printed customer branding resolves through documentBrandingProfile using canonical job/customer/site links and explicit use_print_branding; customer logo displays resolve fresh signed URLs, and all PDF/Word header loaders try the generating-org logo on failure — why: private storage and broken customer images must not leave blank headers or alter saved references.
- Shared PDF/Word paperwork uses printText for print-only identity/history formatting and company-scoped colour fallback in documentBrandingProfile; question row heights include all wrapped lines and blank-answer cells retain borders but no internal rules — why: print polish must not mutate source records, truncate questions or remove signing lines.
- Job riser print controls share VisitPaperwork's action row, keeping the sticker action independent of sheet availability and reusing the existing blank-sheet generator — why: layout changes must not replace per-riser engineer paperwork or hide sticker printing.
- Site access is stored separately from publicly/customer-readable sites in staff-only org-scoped tables; writes and immutable history use save_site_access_info, and only blank engineer PDF/Word builders fetch it — why: customer outputs and public QR routes must never inherit codes from site joins.
- Recent-feature writes validate linked row ownership server-side, import/merge lookups page within the current org, asset tags are unique by (org_id, asset_tag), and print issuer/asset fallbacks resolve per session — why: RLS alone cannot protect service-role imports, security-definer child updates or stale company branding.
- Email Triage ops notifications use per-job server-only request tokens and best-effort net.http_post; renewal handlers validate company/admin ownership and dry runs bypass all writes and sends, with admin health via get_email_step_health — why: notification failures must not roll back jobs or silently cross company boundaries.
- Engineer paper sheets resolve through src/lib/printTemplate.ts: the job type's print_template_id (Settings > Documents), then the company's first published template for that job type, then a shared one — why: matching a template by name broke for any service type whose name differs and could pick another company's sheet.
- PO intake job types are matched against the company's own job_categories via supabase/functions/_shared/matchJobCategory.ts (rarity-weighted words, uncertain → needs_type); job type changes go through src/lib/jobCategoryChange.ts — why: no fixed lists, every subscriber uses its own types and paperwork follows the type.
